## High severity

### 1. The demo dataset (Breast Cancer Wisconsin) can no longer be run from the UI at all
- **File**: `src/ui/app.py` (sidebar section)
- **Finding**: the UI rewrite dropped the old "Demo dataset / Upload your own CSV" radio toggle
  entirely - the sidebar is now upload-only. `run_baseline()` (the function that runs the built-in
  dataset with no upload) still works and is untouched, but nothing in the UI calls it any more.
- **Evidence**: confirmed by diffing `app.py` against HEAD and by booting the real app with
  `AppTest` - the sidebar's widget list has no radio and no demo run/loop button.
- **Why it matters today**: `agent_docs/decisions.md` (ADR-020, landed the same day as this rewrite)
  explicitly reasons about Breast Cancer Wisconsin as "the one dataset this project is actually
  walked through" for the demo. No ADR or TODO records this as a deliberate cut - it reads as an
  unintended casualty of the ~500-line restructure.
- **Recommendation**: restore a zero-upload path to run the demo dataset, or state explicitly that
  it was cut on purpose.

### 2. The chronological split silently scrambles order the moment a time column has one unparseable value
- **File**: `src/dataset.py` (`_time_sort_key`), reached from `prepare_uploaded_dataset`
- **Finding**: the UI's own time-column picker (`profiling.detect_candidate_time_columns`)
  tolerates up to 5% unparseable values in a candidate column. `_time_sort_key`, which actually
  orders the chronological split, parses with no such tolerance (`errors="raise"` by default) and
  falls back to sorting by the raw, un-parsed string values on any failure - silently, with no
  warning.
- **Evidence**: reproduced end-to-end via `dataset._split_indices` on a synthetic dataset with 98%
  parseable dates (a valid UI candidate) - the resulting "holdout" (meant to be the latest rows) is
  anchored around dates earlier than rows left in the training set.
- **Recommendation**: use `errors="coerce"` in `_time_sort_key` to match the tolerance already
  promised by the candidate picker, and either sort unparseable rows to a fixed end or raise a clear
  error naming them.

### 3. The feature loop's own revision prompt suggests an idea guaranteed to crash scoring
- **File**: `src/agent.py` (`_build_instruction`'s revision prompt: "Add a feature interaction...");
  `_reindex_to_booster_feature_order`
- **Finding**: holdout scoring only ever uses the dataset's raw columns - it never re-runs the
  modeller's feature-engineering code. If the modeller follows the loop's own suggestion and trains
  on an engineered column, scoring raises a bare `KeyError` on that column name. The failure is
  caught (produces a failure record, not a crash), but the message is just the raw `KeyError` text,
  and the loop's next round is generated from the same prior state - it can repeat the same doomed
  suggestion, burning rounds against the fixed budget.
- **Evidence**: reproduced directly - a booster trained on a `ratio` column raises `KeyError:
  'ratio'` against a holdout frame that only has the raw columns.
- **Recommendation**: stop suggesting feature engineering the pipeline cannot replay against
  holdout, and/or catch this specific case with a clear message, and feed a failed round's reason
  into the next round's revision context.

### 4. `MAX_REVISION_ROUNDS` raised from 3 to 5 with no ADR entry and no TODO line
- **File**: `agent_docs/decisions.md` (ADR-017), `src/feature_loop.py`
- **Finding**: ADR-017 fixes the round cap at 3 and flags it as "worth watching if ever raised".
  Commit `47cdd49` raised it to 5 with a rationale in the commit message, but no ADR update and no
  TODO line record the change - the exact process gap CLAUDE.md's decision-log rule exists to close.
- **Recommendation**: add a short ADR entry (or a dated addendum to ADR-017) recording the change.

### 5. ADR-001 is not marked superseded by ADR-023, unlike every other superseded ADR in the log
- **File**: `agent_docs/decisions.md` (ADR-001, ADR-023)
- **Finding**: ADR-023 itself states that ADR-001's "Deployment stays simple, no Dockerfile" line is
  now superseded. ADR-001's own header still reads plain "accepted", unlike ADR-002 which correctly
  carries a "Status: superseded by ADR-008" pointer - the file's own established convention.
- **Recommendation**: update ADR-001's status line to point forward to ADR-023.

## Medium severity

### 6. `run_evaluation.py`'s printed table mislabels regression R² as "accuracy", with no column to tell the tracks apart
- **File**: `scripts/run_evaluation.py`, `src/agent.py` (`holdout_accuracy = r2` for regression)
- Since ADR-019, `holdout_accuracy` is overloaded to hold R² for regression rows, but the printed
  table's column is hardcoded `'accuracy'` with no `task_type` column - two rows both labelled
  `target_leakage` (one per track) show numbers that mean different things with no way to tell which
  is which from the terminal output alone (the JSON summary does carry `task_type`).
- **Recommendation**: add a `task_type` column and label the metric per-row.

### 7. A mid-loop steering instruction can leak from a finished loop into a brand-new one
- **File**: `src/ui/app.py` (`mid_loop_instruction_input`, `_start_feature_loop`)
- The instruction textbox is only cleared when a round completes within the same loop -
  `_start_feature_loop` never resets it, so starting a new loop after a previous one can silently
  carry over stale text into the new loop's revision context.
- **Recommendation**: reset the instruction key at the top of `_start_feature_loop`.

### 8. The winner banner's "Rounds run" metric contradicts the winning-round number
- **File**: `src/ui/app.py` (`_render_loop_result`, winner branch)
- `len(loop_result.attempts)` (non-failed rounds only) is shown as "Rounds run" next to "Winning
  round", which uses the full round index - on a loop with failed rounds this renders a winning round
  number higher than the total rounds shown, reading as a live contradiction. The sibling "no
  accepted baseline" branch already uses the correct `rounds_attempted` counter.
- **Recommendation**: use `rounds_attempted` here too.

### 9. README self-contradicts on whether Langfuse tracing is unconditional
- **File**: `README.md`
- The intro states "Every run is traced to Langfuse"; the Setup section correctly says tracing is
  optional and the app runs fine without it (confirmed empirically - tracing degrades gracefully
  with no keys set).
- **Recommendation**: soften the intro line to match Setup.

### 10. README omits the macOS `libomp` dependency ADR-003 specifically flagged for this file
- **File**: `README.md`
- ADR-003 records the exact reason this note is needed (a `dlopen`/LightGBM crash on a fresh macOS
  clone) and says README's setup instructions should mention it. They don't.
- **Recommendation**: add a one-line `brew install libomp` note to Setup.

### 11. Code before `_run_baseline_async`'s own `try:` block can crash with no run record
- **File**: `src/agent.py` (CSV read, `dataset_id` hash, profiling - all before the `try:`)
- The module's own guarantee ("a failed run always leaves a trace") only covers code from the
  `try:` onward; an exception in the CSV read or profiling step (e.g. a corrupted upload) propagates
  with zero `RunReport` saved - a narrower recurrence of the class the first audit closed.
- **Recommendation**: move the `try:` up to cover this block, or add a second narrow handler.

### 12. `RevisionContext`'s 500-character instruction cap lives only in the UI, not structurally
- **File**: `src/agent.py` (`_build_instruction`), `src/ui/app.py`
- ADR-021 states the cap is enforced in `_build_instruction`; it's actually only a `[:500]` slice in
  the Streamlit callback. Any non-UI caller of the loop gets no cap at all.
- **Recommendation**: move the truncation into `RevisionContext` or `_build_instruction` itself, or
  correct ADR-021's text.

### 13. ADR-015 cites two different functions at the same, wrong, line number
- **File**: `agent_docs/decisions.md` (ADR-015)
- Both `build_run_report_from_execution` and `_reindex_to_booster_feature_order` are cited as
  `src/agent.py:224`; their real current locations are 290 and 371 respectively.
- **Recommendation**: drop line-number citations from the decision log, or fix them.

### 14. `pydantic` and `numpy` are used directly but not declared as direct dependencies
- **File**: `pyproject.toml`
- Both are imported directly in `src/critic.py`/`src/agent.py`/`src/evaluation.py`, but resolve only
  via `google-adk`'s and `pandas`'s transitive requirements today.
- **Recommendation**: add both as explicit direct dependencies.

### 15. `ipykernel` is declared but has zero usage anywhere in the repo
- **File**: `pyproject.toml`, `notebooks/` (contains only `.gitkeep`)
- Appears to be leftover project-template scaffolding.
- **Recommendation**: remove it, or note it's intentionally kept for future notebook work.
